# 先计划后实施

仅显式调用时启动。以当次需求为范围，先研究并写出计划，用户确认后实施。同一计划的后续修改、确认和继续执行无须重复调用本技能。

## 研究需求与现状

1. 阅读相关仓库约定，定位需求涉及的入口、调用关系、现有实现和可复用能力。研究到足以确定改动位置与实施顺序即可。
2. 区分代码中已存在的事实、拟采用的设计和仍待确认的假设。引用真实文件与函数；拟新增的位置明确标注，不能将历史计划当作当前代码事实。
3. 只有影响实施方向且无法合理推断的关键问题才询问用户。问题附建议选项；能够自行决定的实现细节直接写入方案。
4. 规划阶段只做读取和分析，文件写入仅限本次计划文档。实现、安装依赖或修改外部状态等操作留到实施阶段。

## 生成与保存计划

1. 写入前检查工作区根目录下的 `hiduck/plan/`。目录不存在时，提示用户先创建；确认目录已存在后才写入，不代建、不改存到其他位置。
2. 新计划命名为 `YYYY-MM-DD-需求短名.md`，同名时追加递增序号。修改或继续已有计划时更新同一文件，不另建副本或覆盖其他需求的计划。
3. 读取 [计划模板](assets/plan-template.md)，按需求规模裁剪。替换全部占位内容与示意图，删除模板注释和不适用的可选章节；小需求保持短文档。
4. 文档用简体中文，包含以下信息：
   - 用一句话概括目标与交付范围；必要时说明当前实现、可复用能力、关键决策和实际存在的未决问题。
   - 按依赖顺序列出实施任务。每项写清改动动作、文件或函数位置、必要依赖和可观察的完成结果；接口、数据结构和异常分支仅在影响落地时展开。
   - 提供简洁 Mermaid 图，表达本次需求的业务流程、调用关系或关键判断。节点使用实际模块或动作，图与正文一致。
   - 写明本次采用的轻量校验、无需校验，或用户明确要求的测试范围。
   - 文末保留“计划落地确认点”，汇总实施范围、关键决策、完成判据和 `- [ ] 用户确认按本计划实施`。
5. 文件链接相对计划文档位置解析。例如计划位于 `hiduck/plan/` 时，源码链接使用 `../../src/...`；拟新增文件注明“拟新增”。

## 任务与进度格式

计划使用 YAML 头部字段 `name`、`overview`、`todos`。每个 todo 包含稳定的 `id`、简短的 `content` 和 `status`。任务 ID 使用有含义的小写连字符名称，调整顺序后保持不变。

正文实施任务以 `- [ ]` 加相同 ID 开头，与头部 todos 一一对应。YAML 记录任务状态，正文复选框展示完成情况，两处在同一次文档修改中同步。文末的用户确认复选框不属于实施任务。

| status        | 含义               | 正文标记                  |
| ------------- | ------------------ | ------------------------- |
| `pending`     | 尚未开始           | `- [ ]`                   |
| `in_progress` | 已开始、尚未完成   | `- [ ]`                   |
| `completed`   | 已实际完成         | `- [x]`                   |
| `cancelled`   | 已从本次范围中取消 | `- [ ]`，附“已取消”与原因 |

- 新计划的实施任务均为 `pending`，用户确认项未勾选。按可交付的结果拆任务，不把每条命令拆成独立任务。
- 任务开始时改为 `in_progress`；实际完成后立即改为 `completed` 并勾选正文，按需补一句落地结果。
- 发生阻塞时保留未完成状态，在对应任务下记录阻碍、剩余工作和继续条件。取消项保留记录，不能标为完成。
- 编写测试与执行测试属于不同完成结果；只有用户明确要求测试时才规划相应任务。

## 审阅、调整与确认

1. 计划写好后提供可点击路径及需要确认的关键内容，等待用户按第 3 条发出落地指令。用户的提问、方案修改或沉默都不视为实施授权。
2. 用户修改计划时，在同一文件更新 overview、相关任务、正文、Mermaid 和确认点中受影响的内容。仅已取消的任务改为 `cancelled`；新增任务使用新 ID，保留其他任务状态。
3. 计划文档写完并提供给用户审阅后，只有用户明确发出 `落地 <完整文件名>` 或 `落地 <项目相对路径>`，且所指文件与待实施计划一致，才可开始实施。完整文件名须包含 `.md`，例如 `落地 2026-09-23-初始化uv项目.md` 或 `落地 hiduck/plan/2026-09-23-初始化uv项目.md`。仅说“开始落地”或“确认按计划实施”不构成授权。
4. 收到符合第 3 条的落地指令后，勾选确认项并开始实施；该授权持续适用于同一计划的后续步骤和中断续做，无须逐项重复确认。
5. 普通实现细节和满足原依赖关系的步骤调整可直接处理。代理提出实质改变范围或预期行为时，在确认点列出变更及未勾选的确认项，等待用户按第 3 条再次授权受影响部分；保留此前已完成的记录与仍有效的授权。用户明确指定的变更直接记录到计划，实施仍须符合第 3 条。

## 实施、中断续做与交付

1. 依照已确认计划实施，每完成一项立即回写状态与正文复选框。完成依据是实际交付结果，不要求默认追加测试步骤。
2. 收到继续执行的请求时，先读取对应计划和必要的当前文件，确认已完成项仍符合现状，从未完成且依赖已满足的任务继续。不要重复执行已完成项，也不要仅凭旧勾选忽略实际变化。
3. 多份计划导致目标不明确时，只询问需要继续的文档路径。已有明确计划与授权时直接续做；尚未确认的计划仍先等待确认。
4. 中断或阻塞时及时记录当前进度与继续条件；未完成项保持未勾选。恢复执行时同步更新该记录。
5. 本次范围全部落实后，在确认点之前补充简短落地结果，并报告文档路径、完成内容及实际校验情况。若有取消或阻塞任务，分别说明，不能宣称所有原计划项均已完成。

## 重实施、轻验证

用户未明确要求测试时，不生成测试任务、不编写测试用例、不运行测试套件；按需要做简单校验，也可以不校验。不要因需求属于缺陷修复、计划中出现“验证”字样或套用模板就自动增加测试。

用户明确要求测试时，才编写并执行与要求对应的用例，范围按用户要求确定。未要求全量测试时不主动扩大到全量。文档如实记录做过的校验或测试，以及未执行的部分。
